# 🔄 useMemo - React 的缓存大师

  最后更新: {new Date().toLocaleDateString()}

## 📌 一句话理解

`useMemo` 就像是给你的计算结果安了一个智能开关：**当依赖项不变时直接取缓存值，变化时才重新计算**。

```tsx
const 缓存值 = useMemo(计算函数, [依赖项]);
```

## 🛠️ 核心作用

### 解决什么问题？

当组件频繁重新渲染时，避免重复执行高开销计算：

```tsx
// 没有优化的危险写法
const 计算结果 = 超复杂计算函数(props数据); // 每次渲染都执行

// 使用 useMemo 优化版
const 计算结果 = useMemo(() => 超复杂计算函数(props数据), [props数据]); // 仅在props改变时执行
```

## 🎯 使用场景 && 💡 最佳实践

### 应该什么时候使用？

| 场景类型        | 典型示例          | 优化效果              | Demo                                               |
| --------------- | ----------------- | --------------------- | -------------------------------------------------- |
| 大数据计算      | 数组过滤/排序     | 减少不必要的 CPU 消耗 | <MdxTableLink src="/lab/useMemo" str="跳转示例" /> |
| 组件 Props 传递 | 向下传递对象/数组 | 避免子组件无效重渲染  |                                                    |
| 第三方库集成    | 图表配置/动画参数 | 防止意外重新初始化    |                                                    |
| 依赖项对比      | 复杂对象作为依赖  | 精确控制更新时机      |                                                    |

## ⚠️ **常见陷阱**

```tsx
// 错误 1：忘记依赖项
const total = useMemo(() => a + b, [a]); // ❌ 当 b 变化时不会更新

// 错误 2：滥用缓存
const sum = useMemo(() => 1 + 2, []); // ❌ 简单计算反而更慢

// 错误 3：副作用操作
useMemo(() => {
  fetchData(); // ❌ 副作用属于 useEffect
}, []);
```

## 🚨 可能忽略的细节

```tsx
// 看似优化实则更糟的案例
const data = useMemo(() => {
  return props.items.filter(x => x > 10).map(transformFunc);
}, [props.items]); // 当 transformFunc 变化时不会更新！

// 正确写法应该包含所有依赖
}, [props.items, transformFunc]);
```

## 🧠 高频面试题

### 1.useMemo 和 useCallback 有什么区别？

**useMemo** 缓存计算结果，**useCallback** 缓存函数本身

**useCallback(fn, deps)** 等价于 **useMemo(() => fn, deps)**

### 2.什么时候应该避免使用 useMemo？

计算非常简单（如基本类型运算）

依赖项频繁变化导致缓存失效

### 3.为什么我的 useMemo 没有生效？

检查：依赖项是否正确？计算函数是否真的昂贵？是否在渲染期间修改状态？

## 🤔 延伸思考：框架哲学差异与优化本质

当我深入思考 React 的 useMemo 时，不可避免地需要将其置于前端框架的设计哲学坐标系中进行对比。
以 Vue 作为参照对象，我们会发现两者在渲染机制上的根本性差异，以及由此产生的不同优化策略。

| 特性             | React                        | Vue                       |
| ---------------- | ---------------------------- | ------------------------- |
| **更新触发机制** | 父组件渲染触发子组件递归渲染 | 依赖追踪触发精确更新      |
| **数据响应原理** | 不可变数据 + 手动优化        | Proxy 代理 + 自动依赖收集 |
| **组件更新粒度** | 组件级更新（默认）           | 元素级更新（默认）        |
| **优化策略重心** | 开发者显式控制               | 框架自动优化              |

### <MdxNormalLink src="/" str="如果你想要了解 Vue 的响应式原理" disabled />

虽然 Vue 默认高效，但仍提供多层次优化手段：

1. **v-once 指令** 静态内容渲染一次后不再更新

2. **shallowRef** 与 **shallowReactive** 浅层响应式数据，避免深层变更触发渲染

3. 或者直接在**setup**中手动控制渲染逻辑

### 框架哲学碰撞

| 维度             | React                | Vue              |
| ---------------- | -------------------- | ---------------- |
| **设计目标**     | 构建可预测的大型应用 | 快速开发高效应用 |
| **优化心智模型** | "你掌控一切"         | "默认最优解"     |
| **学习曲线**     | 陡峭但灵活           | 平缓但约束       |
| **典型应用场景** | 复杂交互型应用       | 内容驱动型应用   |

通过对比可见，React 的 useMemo 不是银弹，而是框架设计哲学下的必要工具,在获得更自由的掌控下同时也增加了更多的心智负担。
Vue 的自动优化虽减轻心智负担，但也意味着放弃部分控制权。
开发者应当理解底层机制，根据项目特点选择合适的优化策略，在工程效率与性能追求之间找到最佳平衡点。
